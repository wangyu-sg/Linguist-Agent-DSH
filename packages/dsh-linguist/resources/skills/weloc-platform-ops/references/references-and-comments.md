# WeLoc TM/TB、批注引用与 QA 口径

> **观察范围说明**：以下行为源自对特定 WeLoc 前端版本的观察与平台采证经验；实际操作时结合当前页面提示与本项目要求核实。

## 1. TM / TB / 评论面板异步刷新与候选覆盖风险

- **异步刷新与延迟残留**：
  - TM、TB、评论面板为异步刷新，报告所见部分入口带有 `600ms` 节流；切段或切换右侧页签后，面板正文可能尚未随新段/新页签同步更新。
  - **已观察实例**：曾出现已选中 `TB` 术语页签，但面板正文短暂仍显示上一页的 `TM` 匹配，待正文标题切换为术语后才真正展示本段 TB 结果。若在切换后立即抓取文本，极易把上一段或上一页签的候选误归属给当前句段。
- **采集与插入保护**：
  1. 采集任何候选前，必须同时核对**当前选中行身份**与**面板实际显示的标题及源段对应关系**；看实际已就绪状态即可，不要把源码里的 `600ms` 写成每次必等死时间。
  2. 区分「确实已查无结果」「仍在加载」与「读取失败」，缺少足额区分依据的候选不得混入已完成覆盖，标为「未核实」。
  3. **慎防误点复制覆盖**：TM 面板上的复制动作可能直接覆盖当前句段的译文内容；只读采集时只读取候选原文、译文、匹配度与来源信息，绝不触发会修改译文的复制/应用按钮。
  4. 非编辑态下直接点击插入候选依赖编辑器实例异步创建与延迟，容易丢失或插入到错误焦点；需要采纳候选时，先进入对应行的活跃编辑态再核对结果。

## 2. 长度面板 `max_length` 与项目规范冲突

- 面板暴露的 `max_length` 与上下文 `Context`（如 `context`、`desc`、`context_chs` / `context_en`）中写明的每行字符数、行数要求可能并不一致（例如同时存在 `27` 与 `43` 的不同上限）。
- **处理原则**：采集与审校时同时保留双方的原始来源、数值和计量单位；遇到冲突时作为项目约束问题记录并按本批适用客户文档判断，不可简单用页面面板里的数字覆盖客户文档要求。

## 3. 批注引用机制与失败恢复

- **服务端全文核对**：在所观察版本中，批注引用提交时会把引用所基于的完整文本与服务端保存的全文比对。
- **导致引用失效的常见原因**：
  - 本地有尚未提交到服务端的草稿（尤其在 CMS 失焦只存本地的场景下）。
  - 空白符或换行处理差异（例如本地与服务端对换行归一化或空格的差异）。
- **恢复与防破坏方法**：
  - 提交批注引用失败时，不要反复发送同一个失效引用；先检查当前文本是否已真正保存到服务端，并核对当前行实际文本与换行后，按当前渠道允许的原生方式保存或重新选定文本再重试。
  - 回填需要修改已有批注句段时，优先尽量保留未改文字或仅修改差异片段；修改并保存后，重新核对原有批注是否仍正确关联，并检查新增/保留批注无重复。

## 4. QA 三种口径差异与映射要求

- 在该版本中，**文件级 `quality_count`**、**行级 `quality_status`** 与 **导出 QA 报告中的 `Position`** 三者统计口径并不相同，总数不等于行计数或导出序数属常见设计差异。
- **作业规范**：
  1. 不要看到文件 `quality_count` 与当前页行告警数或导出条数不一致就直接当成平台漏检，先核对各自口径及筛选范围。
  2. 利用导出 QA 报告跳转或回填修复时，必须将报告里的位置信息映射回稳定的文件与句段身份（`file_uuid`、`id`、`key`、`local_index`），绝不能只按导出报告里的 `Position` 序号直接修改网页对应行。
  3. 执行平台 QA 后需等待本轮检查实际完成并核对最新结果；确认修复真实问题与忽略误报按各自授权执行，不可只为消除告警而点击忽略或推动确认阶段。
